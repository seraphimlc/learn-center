# 知行学堂 · 数据规模与分片原则

日期：2026-10-15

## 规模口径（唯一真相）

| 口径 | 数值 | 含义 |
|------|------|------|
| 业务注册 | **约 3 万** | 客户 RFP / 合同对齐 |
| DID 设计容量 | **约 30 万** | 缓存、连接池、异步、扩容切点按此预留 |
| 峰值并发在线 | **约 1 万** | 心跳/进度/首页读参考 |
| ~~百万注册~~ | **不做** | 已废弃旧口径 |

## 诚实结论：当前阶段 **不需要分片**

粗算（30 万用户、人均学 20 课时进度行）：`study_progress` ≈ 600 万行量级，单表 MySQL 8 + 现有索引仍可接受。  
业务 3 万时更只有几十万行。**过早分片会增加双写/路由/运维复杂度，一期收益为负。**

代码中 `vlp.shard.enabled` 默认 **false**，仅为下一迭代开关占位，**不是半实现假分片**。未启用时不应假设存在 `study_progress_0..N`。

## 何时才考虑分片

同时满足再评估：

1. 单表行数接近 **千万**（稀疏完成行通常远低于此）  
2. 其他写路径（注册/审计/访问日志）压满主库且已做完连接池/索引优化  
3. 有专人维护双写校验与滚动迁移工具  

## 候选表与键（原则）

| 表 | 是否优先 | 建议分片键 | 说明 |
|----|----------|------------|------|
| `study_progress` | 首选 | **userId % N** | 学习读几乎总带 userId；与「我的学习」对齐 |
| `visit_log` | 次选 | 时间分区（按月）优于 user 分片 | 写多读聚合；冷数据归档 OSS |
| `audit_logs` | 次选 | 按月分区 | 审计保留期后归档 |
| `users` / `courses` / `lessons` | 否 | — | 维度表，30 万内无需分片 |
| `notifications` | 观望 | userId | 仅在通知爆炸时 |

**不建议按 courseId 分 progress**：学员「我的学习」跨课聚合会打多片。

## 迁移路径（未来）

1. N=16 起，`shard = userId % N`  
2. 双写期：旧表 + 新分片表并行，校验工具比对  
3. 读切分片 → 停双写 → 归档旧表  
4. （已取消进度 flush）多实例只需共享 Redis；进度无 DB 争用  

## Redis vs MySQL（本系统）

| 用途 | 落点 | 是否恰当 |
|------|------|----------|
| 进度高频写（position） | **Redis only**（TTL 7–30d） | ✅ 心跳永不 flush MySQL |
| 课时完成标记 | 稀疏 MySQL 一次 | ✅ 证书 / 导出 |
| 首页匿名壳 | Redis Cache TTL 30s | ✅ 读多写少 |
| 限流计数 | Redis 固定窗口 | ✅ 短命、可丢 |
| 微信 OAuth state | Redis TTL 10m | ✅ 一次性 CSRF 令牌 |
| 用户/课程主数据 | MySQL | ✅ 权威源 |
| AI 缓存 | MySQL `ai_cache` | ✅ 可持久；非热点可不进 Redis |

**播放进度以 Redis 为权威（ephemeral）**：TTL 默认 14 天，过期可丢。MySQL `study_progress` 不再承接心跳；仅稀疏完成行。若未来要「永久续播」，需另开需求做可选落库，而非恢复高 QPS flush。
